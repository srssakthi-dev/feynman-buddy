# Local candidate comparison v1 — protocol fixed before execution

Compare installed llama3.2:latest and qwen3.5:4b using the existing conversation-v2 and reflection-v2 prompts and actual inference functions. Save model digests, quantisation metadata, Ollama version, prompt text, inference/case hashes, full request messages, raw output, cleaned reflection, errors and stage timings. Do not alter live sessions or the application's default model during the experiment.

Ten synthetic development cases: seven conversation probes (including two different legitimate natural-number conventions), three reflection probes. Cases are authored before either model runs and include explicit acceptance criteria. Known gradient-descent and Sets failures informed these fixtures, so they are not held-out cases. No copyrighted notes or personal user transcript is embedded in this fixture.

Fixed short source passages isolate response generation and attribution from retrieval. Both candidates receive identical cases, source context, prompts and common inference settings; thinking is explicitly disabled for Qwen, which supports that capability. The existing prompt was developed with Qwen, an acknowledged source of selection bias. No claim of an architecture-independent best model is warranted.

Run sequentially in candidate blocks (Llama then Qwen) to avoid concurrent model requests from this runner. Ask the user to avoid app inference during the run; shared-server contention cannot be ruled out. Do not unload user models or stop user application servers. Each candidate receives the same case order. One sample per case with temperature 0.2 and seed 42; a shared seed does not imply equivalent sampling across architectures or universal reproducibility.

Review each output against its case-specific criterion: pass, partial or fail, with an explicit reason. Report conversation and reflection results separately, not a single misleading accuracy score. Also inspect unsupported factual claims, leading questions, assistance attribution, evidence validity and generation truncation. An empty reflection cannot earn credit where the case requires a supported observation. Structured-output validity and semantic correctness are separate outcomes.

The initial output review is performed by the coding assistant, not an independent human assessor. Mark it provisional and provide raw outputs for student review; do not report inter-rater agreement or user-study results. No automatic LLM judge is used. A reasonable candidate choice prioritises avoiding incorrect educational feedback and meeting reflection evidence requirements, while accounting for observed response delay. A faster but misleading candidate is not automatically preferred. If neither is adequate, retain the current development default provisionally and report the unresolved limitation rather than proclaim a winner.

Report total call latency and Ollama load/prompt/generation timing where available. Separate conversation and reflection summaries. Initial calls may include loading; do not label all later calls warm without inspecting the load trace. One sequential run is not a controlled speed benchmark. Include every failed call and denominator; do not silently retry or exclude failures.

Execution: set PYTHONPATH=backend; run evaluation/build_comparison_cases.py once, then evaluation/run_local_comparison.py using the existing project Python environment. The runner refuses to overwrite prior raw results. Results go to evaluation/results/local_comparison_v1. Following review, write the decision and report implications before any production model change.
